# Codex + Cursor Playbook

## 目标

把“会用 AI 写代码”升级为“可持续交付”：
- 任务可委派（目标明确、边界清晰、可验证）
- 结果可审查（测试证据、风险说明、人工把关）
- 经验可复用（沉淀为 Skill，在 Codex 与 Cursor 中复用）

## 快速使用

1. 先判断当前请求属于哪类：问答、委派、接入、治理。
2. 将需求改写成“委派任务单”（见下方模板）。
3. 明确环境约束：仓库范围、是否联网、禁止修改项、验证命令。
4. 收到结果后，按“审查清单”验收，再决定继续迭代或创建 PR。
5. 若任务会重复出现，沉淀为 Skill（脚本/参考/模板）。

## 任务分类与处理策略

### A. 问答模式（解释能力与边界）

输出结构：
- 先给结论（能做/不能做/代价）
- 再给 3-5 步可执行方案
- 最后给风险与人工检查点

### B. 委派模式（让代理执行代码任务）

必须包含：
- 目标：改什么、达到什么行为
- 范围：允许改哪些文件/目录
- 验收：测试、lint、类型检查、运行截图/日志
- 禁止项：不改 API、不改迁移、不动敏感配置
- 交付：变更摘要 + 证据 + 未决风险

### C. 接入模式（Codex/Cursor/GitHub）

重点关注：
- 仓库授权与最小权限
- 环境一致性（依赖、工具链、测试命令）
- 是否允许联网与外部依赖下载
- PR 门禁（CI 通过、评审通过、回滚方案）

### D. 治理模式（团队化落地）

落地顺序：
1) AGENTS.md 约束（编码规范、命令、禁区）
2) 统一任务模板（减少提示词漂移）
3) 审查清单（质量、风险、可维护性）
4) 复盘机制（把高频问题写回 Skill）

## 标准委派模板（可直接复用）

将以下模板改写后交给 Codex/Cursor 代理：

```text
任务目标：<一句话说明要实现的结果>

代码范围：
- 允许修改：<目录/文件>
- 禁止修改：<目录/文件>

实现约束：
- 保持现有对外 API 不变（除非明确要求）
- 不引入新的运行时依赖（除非明确批准）
- 优先最小改动与可回滚

验收标准：
1) 单元/集成测试通过：<命令>
2) 代码质量检查通过：<lint/typecheck 命令>
3) 行为验证：<复现步骤或预期输出>

交付格式：
1) 变更摘要（按文件）
2) 验证证据（命令 + 结果）
3) 风险与未完成项
4) 建议下一步（是否可开 PR）
```

## 并行代理拆分模板

适用于中大型任务：
- 子任务 1：核心实现
- 子任务 2：测试补齐与回归
- 子任务 3：文档/迁移说明

合并要求：
- 不同子任务避免修改同一热点文件
- 统一验收标准
- 最终由人工做一次整体验收

## 审查清单（合并前）

- 功能正确：满足需求且无明显回归
- 测试充分：新增/变更路径有覆盖
- 代码可维护：命名、结构、注释合理
- 风险透明：边界条件、失败路径已说明
- 可回滚：改动粒度可控，回退路径清晰

## Skill 设计守则（供二次沉淀）

- frontmatter 尽量仅保留 `name` 与 `description`，提升跨实现兼容性。
- `description` 写清“做什么 + 何时触发”，这是自动调用的核心信号。
- 主 `SKILL.md` 保持精简；细节放到 `references/` 按需加载。
- 重复且易错的步骤，优先固化为 `scripts/`，避免每次重写。
